# Brief — Fix the harness before you switch models

## Reader and promise
Engineers and tech leads who run AI coding agents and are tempted to swap models when results disappoint. Promise: a numbered harness audit — context, verification, state and progress files, and tools — that you can run on your own setup in about an hour, so you know whether to change the harness or the model.

## Counterpoints
- The model still sets the ceiling on hard tasks. In Garry Tan’s seven-harness matrix, three of the 20 tasks never passed in any cell, on Opus 5.5 or on GPT-6.1 Sol. Eleven tasks passed everywhere. The run could not separate harnesses on pass rate, and the authors say to raise the task ceiling before ranking harnesses again (claim 4). Anthropic’s later write-up makes the same point from the other direction: when the model gets better, scaffolding built for an older limit becomes load-bearing for nothing and should come out; new, harder work then needs new scaffolding (claim 11).
- Swapping harnesses did not produce a detectable pass-rate gain on those 20 tasks. “Fix the harness before you switch models” is not the same as “your pass rate will jump.” What moved, on that set, was cost and speed (claims 2 and 3).
- Some public harness gaps are partly benchmark artifacts, not controlled ablations. Terminal-Bench 2.1’s task fixes alone moved Claude Code with Opus 4.6 by 12.1 points and flipped its standing against Terminus 2 with the same model (claim 8). Public leaderboard rows can also differ in date, token budget and reasoning effort; they are not a randomized swap of the harness alone.
- A heavier harness can cost much more for the same measured pass rate on easy tasks (OpenClaw about 2× Claude Code on Opus in Tan’s matrix; claim 3) or 20× more in Anthropic’s internal game-maker comparison (claim 10). Cost is part of the decision, not just the headline score.

## Examples / data
Use these four checks as the numbered audit. Each one is something you can inspect in your own setup; the figures above are evidence that the check matters, not scores you should expect to copy.

1. **Context.** What is injected every turn (system prompt, `AGENTS.md` / `CLAUDE.md`, tool schemas, memory files)? How large is it? Are huge tool outputs re-sent in full? Osmani describes context rot and the usual countermeasures: compaction, offloading large tool results to disk, and loading skills only when needed. Tan’s cost run found most of OpenClaw’s extra spend was cache writes from a bigger prompt and bigger tool results (claim 6). On harder tasks, stripping Claude Code’s memory text and tool advice together collapsed pass rate from 60.4% to 0% (claim 5) — so “trim context” is not free. Check where a must-follow rule actually lives: a one-time note fades; a per-turn hook or system-prompt line was followed in 30 of 30 turns (claim 12).
2. **Verification.** What, other than the builder, is allowed to call the work done? Anthropic saw agents mark features complete after unit tests or `curl` while the product was still broken end-to-end, and saw agents grade their own work too kindly (claims 9 and 10). Look for hooks that run typecheck, lint or tests and feed failures back; a done-list that starts failing; and, if you have it, a separate evaluator with no write access to the code it is grading.
3. **State and progress files.** Can a fresh session reconstruct where the last one stopped without guessing? Anthropic’s working pattern is a progress file, a feature list that starts as failing, git history with descriptive commits, and a startup script (claim 9). If your agent “finishes” a multi-hour job in one context window, or leaves half-written work undocumented, this layer is missing.
4. **Tools.** How many tools are on the menu, and does the agent actually use the ones you rely on? An unmentioned skill sat unread on Claude Code and Hermes (0 opens in 30 turns) until the prompt named it (claim 12). Anthropic saw better bug-finding once the agent had browser tools and was told to test as a user would (claim 9). Prefer a short, named tool list over a pile of overlapping MCP servers.

**How to read the evals.** Tan’s matrix and findings are labeled dev results on public tasks at pinned versions, not held-out confirmation. Claude Code and Codex are never compared with each other because each can run only its own model. Two OpenClaw cells were incomplete (cap stops on the last task). QM ran on a different Docker network, so its pairs were not tested. Tan discloses that he runs the evaluation and related projects, that QM is a Y Combinator project, and that Y Combinator is an investor in Hermes. The scoreboard table is at https://github.com/garrytan/g-harness-evals/blob/1c26ae409de0c90c32f5becd33a2aa7c311e7ef7/docs/scoreboard.md.

**Terminal-Bench 2.0 in one line.** It is a harder, re-verified set of container tasks (89 in 2.0) scored as agent-model pairs, not as models alone: https://www.tbench.ai/news/announcement-2-0.

## Open questions
- On a harder, off-ceiling task set (Tan’s planned v0.4 rerun, or your own failing tickets), do harnesses separate on pass rate, or do the same hard tasks still fail in every harness?
- How much of any public leaderboard gap is harness design, and how much is token budget, reasoning effort or broken tasks?
- When a task never passes in any current harness — like Tan’s three corrections tasks — is the next move a stronger model, a better verifier, or a different task breakdown?
- What is a cheap first measurement for a team: ten of your own recent tickets, with and without your current progress-file / test-hook setup, before you pay for a model swap?
